# Bug 审查报告（B#，9 条）

## B1 中：超时/取消路径下子进程未随 AbortSignal 终止，且工具超时上限可能被流程总和超过
- **位置**：`src/forge.ts:647,682,689,505`；`src/utils.ts:46-82`
- **问题**：`exec.signal` 只传给了子代理，`verifyBuildInTarget` 的 `pnpm install/build`、`git push`、`dsh plugin add` 全部走 `runCommand`，而 `runCommand` 不接收 AbortSignal、被杀后也无 kill。工具级 `timeoutMs: childTimeoutMs`（默认 45 分钟）框住整个流程，但子代理 + install + build 每步各自 45 分钟，三阶段累加远超工具超时。
- **触发场景**：子代理跑满 45 分钟后进入目标目录 install/build（最长又 45 分钟）；调用方已超时/取消，install/build 成为孤儿进程继续占用 CPU/仓库锁。
- **建议**：`runCommand` 增加可选 `signal` 参数透传 `exec.signal`；子代理超时与构建超时设计为互不叠加（如工具超时 = `childTimeoutMs * n`）。

## B2 中：Windows 下 pnpm/npm/npx/dsh 经 `cmd.exe /c` 拼接命令行，含空格参数可能被拆断或误解析
- **位置**：`src/utils.ts:38-43`（`resolveSpawn`）
- **问题**：`resolveSpawn` 对 pnpm/npm/npx/dsh 返回 `cmd.exe` + `['/d','/s','/c','pnpm.cmd', ...args]`。Node 对非 shell 子进程参数按 `CommandLineToArgvW` 规则加引号，与 `cmd.exe /c` 的引号解析规则不一致（已知 footgun）。含空格的参数（`dsh plugin --profile web add link:C:/Program Files/...`、含空格的目标根）会被 cmd 拆分。
- **建议**：对 cmd 转发的命令做显式 cmd 级转义（空格路径整体双引号 + `^` 转义元字符），并加单测覆盖含空格路径场景。

## B3 中：目标目录存在性检查与 `copyInto` 之间隔了整个子代理开发期，跨进程场景会静默覆盖目标
- **位置**：`src/forge.ts:417,488`；`src/migrate.ts:26-33`
- **问题**：`targetExists` 在子代理启动前检查（L417），真正 `copyInto` 在子代理完成后（L488，中间隔了长达几十分钟的子代理运行）。`activeForge` 互斥只挡同进程同名调用，挡不住另一 DSH 进程/脚本在子代理运行期间创建或改写目标目录；而 `copyInto` 用 `cp({ force: true })` 无条件覆盖同名文件。
- **建议**：`copyInto` 前重新做目标存在性/变更守卫，或先复制到目标旁临时目录、校验后再原子 rename/合并。

## B4 低：`inject` 为字符串时 `Object.keys(inject)` 得到字符下标而非服务名
- **位置**：`src/verify-load.ts:80`；`src/hotmount.ts:28`
- **问题**：两处都用 `Array.isArray(mod.inject) ? mod.inject : Object.keys(mod.inject)`。若插件以字符串形式声明 `inject: 'commands'`，`Object.keys('commands')` 返回 `['0',...,'7']`（字符下标）。verify-load 会误判为 unmockable 跳过（误放行），hotmount 会因 `ctx.get('0')===undefined` 拒绝挂载（误阻断）。
- **建议**：统一归一化：`typeof inject === 'string' ? [inject] : Array.isArray(inject) ? inject : Object.keys(inject ?? {})`。

## B5 低：cache-busting 用毫秒级 `Date.now()` 作 URL 查询串，同毫秒重复挂载/校验命中 ESM 缓存
- **位置**：`src/hotmount.ts:21`；`src/verify-load.ts:71`
- **问题**：`?forge=${Date.now()}` / `?verify=${Date.now()}` 只有毫秒精度，同毫秒内两次 import 命中 V8 模块缓存，第二次拿到旧实例，更新不生效。
- **建议**：自增计数 + 时间戳组合（`?v=${Date.now()}-${seq++}`）。

## B6 低：`childReport`/`child.text` 的 `.slice(0, 500)`（及 1500）可能从 UTF-16 代理对中间断开
- **位置**：`src/forge.ts:454,470,581,252,269`
- **问题**：JS `slice` 按 UTF-16 码元截断；emoji/生僻字是代理对，截断点落在中间时留下孤立 surrogate，`JSON.stringify` 转义为 `\udXXX`，下游严格 UTF-8 解码可能报错或替换为 U+FFFD。
- **建议**：截断前用 `codePointAt` 判断断点是否在代理对中间，必要时回退一个码元。

## B7 低：`buildCommitSubject` 长度预算未兜底极长 `name`，commit 主题可超 72 字符
- **位置**：`src/utils.ts:200-212`
- **问题**：`budget = 72 - prefix.length`；当 `name` 很长使 `prefix.length >= 72` 时 `clipped=''`，返回 `` `${type}: ${name}` `` 仍可远超 72；`commitType` 仅校验格式不校验白名单。
- **建议**：`name` 与 `type` 一起纳入 72 字符预算并截断。

## B8 低：`cleanupStaleStaging` 按 mtime 清理整目录，可能误删尚在构建/被锁的 staging
- **位置**：`src/forge.ts:333-357,414`
- **问题**：TTL 开启时每次 forge 先清理；仅保护 `.pnpm-store`，mtime 早于 cutoff 的活跃 staging（另一进程正在构建、或 retry 等待中）会被误删。
- **建议**：排除 `activeForge` 在用的 name 目录，或加"最近写时间"活跃探针；默认关闭即可，先把风险点注释清楚。

## B9 低：登记表 `upsertRepo` 为"读-改-写"非原子，跨 name 并发 forge 可能丢条目
- **位置**：`src/registry.ts:69-78`
- **问题**：`loadRegistry()` → 修改 → `saveRegistry()`（单次写原子，整体读改写不原子）。同名由 `activeForge` 挡住；不同 name 的并发 forge 会各自读到旧 registry，后写覆盖先写。
- **建议**：确认 `isConcurrencySafe:false` 的全局串行语义；不能保证则给 `upsertRepo` 加进程内互斥写锁，或在保存前二次校验。

## B10 已撤销（勘误）：smoke 断言"反转"系误读，实际逻辑正确
- **勘误过程**：初稿将 `scripts/smoke.mjs:111` 误读为 `stat(path.join(syncTarget, 'node_modules', 'dep.js'))`，据此判断"文件存在（受保护）时 check 判 FAIL"为断言反转。经 grep 确认真实代码为 `stat(path.join(syncTarget, 'stale.txt'))`：
  ```js
  // scripts/smoke.mjs:107-116（真实内容）
  const removed = await syncRemoveStale(syncSrc, syncTarget)
  check('syncRemoveStale 删除过期文件', removed === 1)
  let staleGone = true
  try {
    await import('node:fs/promises').then(({ stat }) => stat(path.join(syncTarget, 'stale.txt')))  // ← stale.txt，非 dep.js
    staleGone = false
  } catch { /* 已删除。 */ }
  check('syncRemoveStale 保护 node_modules', staleGone)
  ```
- **正确语义**：`stale.txt` 是 target 独有文件，应被 `syncRemoveStale` 删除；stat 抛错 → `staleGone` 保持 true → check 通过。**断言与语义一致**；`removed === 1` 同时间接证明 node_modules 未计入删除（受保护）。实测：完整运行 smoke（无沙箱限制）exit=0，15 项全绿。
- **残留问题**：check 名称"保护 node_modules"与实际断言对象（stale.txt 已删）不一致，见 M17。

# Perf 审查报告（P#，5 条）

## P1 中：`runCommand` 用 `execFile` 全量缓冲长命令 stdout/stderr（上限 64MB），无流式，超限即判失败
- **位置**：`src/utils.ts:53-61`
- **问题**：`verifyBuildInTarget` 的 `pnpm install/build`、`dsh plugin add`、`git push` 的完整输出都累积为内存字符串直到进程结束；超过 64MB 时 `execFile` 以 `ERR max_buffer_exceeded` 终止，`runCommand` 将其归为"进程级失败"（code -1），误报构建失败且拿不到任何诊断输出。
- **影响**：每次 forge 2~5 个长命令全量驻留宿主内存；输出超大的构建被误杀。
- **建议**：长输出命令改 `spawn` + 流式管道（错误时仅保留尾部如 200KB）；或把 maxBuffer 失败单独映射为带"输出过大"提示的 CommandFailedError。

## P2 低：目标目录的 `pnpm install` 与 staging 安装不共享包仓库，存在整树重复下载
- **位置**：`src/forge.ts:278-283`
- **问题**：子代理在 staging 已 install+build（prompt.ts:107-108），迁移到 target 后又全量重装；prompt 提示子代理 sandbox 拒绝时用 `--store-dir <staging>/.pnpm-store`——一旦走该分支，target 空 store 全新下载；即便全局 store 也要重解析重链接整棵依赖树。
- **影响**：store miss 时 20~120s 网络 + 磁盘，纯冗余。
- **建议**：迁移时复用 staging 的 `.pnpm-store`/node_modules，或显式 `--store-dir` 指向共享 store；核对 `pnpm-lock.yaml` 随迁移复制。

## P3 低：单次 forge 流程中 package.json read+parse≥4 次、registry read+parse≥2 次（随插件数线性增长）
- **位置**：`src/forge.ts:285-296,493-497,537,546`；`src/migrate.ts:46`；`src/registry.ts:69-77`
- **问题**：package.json 在 link 改写、依赖守卫、main/types 校验中各读一次；registry 先 `loadRegistry()` 找 previous，随后 `upsertRepo` 内部又 `loadRegistry()` 一次并 `JSON.stringify` 全量回写。registry 每加一个插件就大一条目，upsert 是 O(N) 读 + O(N) 重建 + O(N) 全量写。
- **建议**：单次作用域内读一次 package.json 复用；`runForgeLocked` 先 `loadRegistry()` 一次并把结果传给 `upsertRepo(registry, entry)`，去掉重复解析与 TOCTOU 间隙。

## P4 低：迁移+提交阶段顺序 spawn 6~7 个 git 子进程（含 `resolveIdentity` 两次独立 `git config`）
- **位置**：`src/git.ts:11-29,32-38,45-58`；`src/forge.ts:524-549`
- **问题**：`git rev-parse` → `git init`? → `git add -A` → `git diff --cached --quiet` → `git config` ×2 → `git commit` →（`git push`）共 6~7 个子进程，每个约 50~100ms；`resolveIdentity` 的两次 config 可合并为一次 `git config --get-regexp` 或直接内联 `-c` 参数。
- **建议**：`ensureGitRepo` 用 `git rev-parse --git-dir` 单次判断；identity 检查合并为单次调用或省略（commitStaged 已支持 `-c` 内联路径）。

## P5 低：`findHarnessRoot` 每次 forge 调用顺序执行最多 10 次 `access`，且循环内动态 `import('node:fs/promises')`
- **位置**：`src/utils.ts:162-182`
- **问题**：配置留空时每次 forge 都从工作区向上逐层 `access` 探测（最多 10 次串行）；动态 import 因 ESM 缓存实际不重复加载，可忽略，但 10 次串行探测未并行也未缓存结果。
- **建议**：按 `startDir` 缓存探测结果；`access` 可改 `lstat` 省一层解析（低优先级）。

**明确未发现**：每轮对话热路径（`selfIterationSectionText` 为常量 join，无 I/O）；大文件流式需求（被读文件均小）；主线程同步阻塞（全程 fs/promises，无 execSync）；正则灾难性回溯（`/(\.\.\/)+deepseek-harness/g`、`/REPORT_START([\s\S]*?)REPORT_END/` 均线性安全）；无界缓存（`activeForge` 有增有删）。

# Maintenance 审查报告（M#，17 条）

## M1 严重：默认值存在三处独立维护源，极易漂移
- **位置**：`src/index.ts:23-57`（z schema `.default()`）、`:60-80`（`DEFAULTS` 对象）、`cordis.patch.yml`（config 段）
- **问题**：同一批默认值（含 `referenceRepos` 四路径整段）手工维护三份。`apply()` 直接合并 DEFAULTS，schema 默认值实际失效或互斥；改默认值（如 author 邮箱）漏改一处即静默不一致。
- **建议**：单一 `DEFAULTS` 为准；schema 改为 `z.object({...}).default(DEFAULTS)` 或由 DEFAULTS 派生默认值；删掉 schema 内重复 `.default()`。
